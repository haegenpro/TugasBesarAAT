# HazardEvent Wire Format Spec

2026-09-20 · @Someone

## Overview

This document fixes the JSON representation of `HazardEvent` used by the Canonical Store, Aggregator read API, and Client API. The Aggregator publishes the equivalent logical fields to NATS as registry-framed Avro; see `Contracts.md` for that wire boundary.

**Applies to:** anyone writing code that produces, stores, or reads a `HazardEvent` — the Aggregator (Person A), the Canonical Store / Client-Facing API (Person B), and Auth-filtered responses / consumers (Person C).

**Target languages:** examples are given in Go and Python. JSON clients use the field table below; broker consumers first decode Avro with the registry schema ID.

## JSON representation rules

| Rule | Decision |
| --- | --- |
| Field naming | `snake_case`, matching the spec's field names exactly (`hazard_id`, `source_ref_id`, ...) — avoids a translation layer in either Go or Python |
| Enums | Encoded as **uppercase strings**, exactly as written in the spec: `"source": "BMKG"`, `"hazard_type": "SEISMIC"`, `"severity": "WASPADA"` — never integers, never lowercase |
| Timestamps | ISO 8601, UTC, millisecond precision, `Z` suffix: `"2026-09-20T14:32:07.123Z"`. Always convert to UTC before serializing regardless of source timezone |
| Floats | Plain JSON numbers (`-6.302`, not strings) |
| Missing/unknown fields | Omit the key entirely rather than sending `null`, unless a field is explicitly nullable per the spec |
| `attributes` | A flat JSON object (`map<string, any>`), values may be string/number/bool — no nested objects unless the source field itself is structured |

**Why this matters cross-language:** Go's `encoding/json` and Python's `json`/`pydantic` both round-trip this shape without custom hooks, as long as everyone commits to the same casing and timestamp format up front. The failure mode we're avoiding is one language guessing `datetime.now()` local time and the other assuming UTC, which silently corrupts `occurred_at` comparisons in P1's severity mapping.

## hazard\_id generation

**Decision: UUIDv4, generated by the Aggregator at mapping time.**

```
hazard_id = uuid4()   # e.g. "a1b2c3d4-5e6f-7890-abcd-ef1234567890"
```

Why not a deterministic hash of `source` + `source_ref_id`: it's tempting (avoids duplicate `HazardEvent`s if the Aggregator ever re-polls the same source record), but it leaks source-identifier structure into the canonical ID, which the spec's separation-of-concerns intent (BMKG/PVMBG internals shouldn't bleed into the canonical layer) argues against. Instead:

- **Idempotency/dedup** is handled separately by keying on `(source, source_ref_id)` internally in the Canonical Store (a unique index), not by deriving `hazard_id` from them.
- Both Go (`github.com/google/uuid`) and Python (`uuid.uuid4()`, stdlib) generate RFC 4122 UUIDv4 with zero extra dependencies.

This only needs to be implemented once, in the Aggregator (Person A) — no other service generates a `hazard_id`.

## Go reference implementation

```go
package canonical

import "time"

type Source string
type HazardType string
type Severity string

const (
	SourceBMKG  Source = "BMKG"
	SourcePVMBG Source = "PVMBG"

	HazardSeismic  HazardType = "SEISMIC"
	HazardVolcanic HazardType = "VOLCANIC"

	SeverityNormal  Severity = "NORMAL"
	SeverityWaspada Severity = "WASPADA"
	SeveritySiaga   Severity = "SIAGA"
	SeverityAwas    Severity = "AWAS"
)

type HazardEvent struct {
	HazardID     string                 `json:"hazard_id"`
	Source       Source                 `json:"source"`
	SourceRefID  string                 `json:"source_ref_id"`
	HazardType   HazardType             `json:"hazard_type"`
	Severity     Severity               `json:"severity"`
	AreaName     string                 `json:"area_name"`
	Latitude     float64                `json:"latitude"`
	Longitude    float64                `json:"longitude"`
	OccurredAt   time.Time              `json:"occurred_at"`
	IngestedAt   time.Time              `json:"ingested_at"`
	Attributes   map[string]interface{} `json:"attributes"`
}
```

`time.Time` marshals to RFC 3339 by default, which matches ISO 8601 — just make sure the value is `.UTC()` before marshaling (`time.Now().UTC()`), since Go's default `MarshalJSON` preserves whatever location the `time.Time` was constructed with.

## Python reference implementation

Using `pydantic` (recommended — free validation + `.model_dump_json()` handles the datetime/enum encoding for you):

```python
from __future__ import annotations
from datetime import datetime, timezone
from enum import Enum
from typing import Any
from pydantic import BaseModel, Field

class Source(str, Enum):
    BMKG = "BMKG"
    PVMBG = "PVMBG"

class HazardType(str, Enum):
    SEISMIC = "SEISMIC"
    VOLCANIC = "VOLCANIC"

class Severity(str, Enum):
    NORMAL = "NORMAL"
    WASPADA = "WASPADA"
    SIAGA = "SIAGA"
    AWAS = "AWAS"

class HazardEvent(BaseModel):
    hazard_id: str
    source: Source
    source_ref_id: str
    hazard_type: HazardType
    severity: Severity
    area_name: str
    latitude: float
    longitude: float
    occurred_at: datetime
    ingested_at: datetime
    attributes: dict[str, Any] = Field(default_factory=dict)

    class Config:
        json_encoders = {
            datetime: lambda dt: dt.astimezone(timezone.utc).strftime(
                "%Y-%m-%dT%H:%M:%S.%f"
            )[:-3] + "Z"
        }
```

If the team prefers stdlib-only (no pydantic dependency), a `dataclass` works the same way but you own serialization by hand — write a shared `to_dict()`/`from_dict()` pair rather than letting each service roll its own, or the casing/format rules above will drift in practice even if everyone agrees to them on paper.

## attributes map: known keys

Per-source keys that land in `attributes`. Client API projects Media responses from an explicit summary field list, so additional raw attributes cannot leak into Media responses:

| Source | Key | Type | Present when |
| --- | --- | --- | --- |
| SeismicEvent | `magnitude` | float | always |
| SeismicEvent | `depth_km` | float | always |
| SeismicEvent | `potential_tsunami` | bool | always |
| TsunamiWarning | `warning_id` | string | when a matching warning exists |
| TsunamiWarning | `related_event_id` | string | when a matching warning exists |
| SeismicEvent | `threat_level` | string | `potential_tsunami = true` and a matching `TsunamiWarning` exists |
| SeismicEvent | `affected_zones` | list\<string> | same as above |
| SeismicEvent | `estimated_arrival` | string (ISO 8601) | same as above |
| VolcanicReport | `eruption_count_24h` | integer | always |
| VolcanicReport | `ash_column_height_m` | float | always |
| VolcanicReport | `confidence_level` | float (0–1) | when present after the schema toggle |

**Unmapped-field policy:** Preserve source fields without a canonical top-level mapping in `attributes` for both BMKG and PVMBG. This includes `confidence_level` when present after `POST /admin/schema-version`, plus later additive source fields. Avro schema evolution lets the Aggregator read the new source record without a restart.

## Static volcano reference table

The Aggregator resolves `latitude`, `longitude`, and `area_name` from the BNPB-owned `volcano_reference` table seeded by `store/init.sql`. PVMBG's seed `volcano_id` values match that table. An unknown ID fails mapping instead of producing fabricated coordinates.

## Cross-language validation checklist

- [ ] Every timestamp field is serialized in UTC with `Z` suffix, verified by round-tripping a sample event between whichever two languages the team actually uses
- [ ] Enum values match exactly, including case (`"SIAGA"` not `"siaga"`) — write one shared sample JSON file (e.g. `docs/sample-hazard-event.json`) and have each service's tests deserialize it
- [ ] `attributes` round-trips as a flat map with no service adding nested objects
- [ ] `hazard_id` is only ever generated by the Aggregator; no other service invents one
- [ ] The unknown-field policy (pass-through vs. drop) declared in the P1 report matches what the code actually does
- [ ] Media-scope responses (P3) are verified against the field table above, not just "looks right" — explicitly assert the four raw fields are absent from that response shape

Keep `docs/sample-hazard-event.json` in the repo and reference it from each service's test suite — it's the cheapest way to catch a wire-format drift before demo day rather than during it.
