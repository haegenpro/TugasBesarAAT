# Aggregator deployment draft

**Implemented, unverified.** No image was built, manifest rendered/applied or
test run for this change. The VMs remain stopped. This renderer prepares the
next deployment component; it does not deploy the sources, broker, registry,
other services or their persistence.

The default profile has three Aggregators, each requesting 256 MiB and limiting
512 MiB. A hostname topology spread constraint uses skew one and at least three
domains. It spreads three pods across nodes and permits the later 3->5->2 scale
sequence on four nodes. Rolling replacement uses zero unavailable and one surge
pod. A PDB requests two available replicas for voluntary evictions. These are
scheduling intentions, not proof of fit, failover or successful rollout. Default
requests add 768 MiB; full Citus plus these pods already exceeds the light VM
allocation before other workloads. VM sizing is unchanged.

The private ClusterIP Service is `aggregator:8080`. `/ready` gates traffic on
store availability and returns unavailable during shutdown; broker degradation
retains the existing read-service behavior. Standbys need not own a source to
serve reads. Startup/liveness use `/health`, so a database outage does not by
itself restart every pod. Termination has a five-second preStop delay, 30-second
HTTP drain budget and 45-second pod grace. Source work is cancelled and drained
before its lease is released. Runtime uses a nonroot UID, read-only root,
temporary scratch volume and no Kubernetes service-account token.

## Inputs and later commands

1. Supply the actual image digest of a build containing these sources. The
   renderer rejects mutable tags. Build context is the existing `aggregator/`
   directory with its env-file exclusions.
2. Bootstrap the storage component and capture its durability config as described
   in [storage setup](../storage/README.md). Stop all old writers/publishers and
   apply administrator migrations through 0006 with the restricted runtime role.
3. Provide BMKG/PVMBG, broker streams and registry with their required persistence
   and credentials. Edit `config.example.json` for their actual service URLs,
   stream names, freshness budgets and `storage_mode` (`postgres` or `citus`).
4. Create the referenced runtime/storage Secrets and captured-config ConfigMap
   privately. No credentials are embedded or generated by this renderer.

The runtime Secret must contain the four keys in `runtime.env.example` with
distinct real credentials according to application configuration rules. Copy it
to a private ignored file first. The storage Secret comes from the storage
generator's `private/application.env`; only DATABASE_URL and relevant group DSNs
are selected. Missing required references keep the pod from starting. The
ConfigMap must contain the captured JSON under key `durability.json`.

Commands prepared for the later integration phase, using default example names:

```sh
docker build -t YOUR_REGISTRY/aat-aggregator:development aggregator
# Push and retain the actual image digest before rendering.
python3 scripts/platform-aggregator.py \
  --image YOUR_REGISTRY/aat-aggregator@sha256:ACTUAL_DIGEST \
  --output evidence/aggregator-resources.json

/var/tmp/aat-m2/cache/k3s kubectl --kubeconfig /var/tmp/aat-m2/secrets/kubeconfig \
  -n sistem-informasi-kebencanaan-bnpb create secret generic aat-m2-aggregator-runtime \
  --from-env-file=evidence/aggregator-private/runtime.env
/var/tmp/aat-m2/cache/k3s kubectl --kubeconfig /var/tmp/aat-m2/secrets/kubeconfig \
  -n sistem-informasi-kebencanaan-bnpb create secret generic aat-m2-aggregator-storage \
  --from-env-file=evidence/storage-postgres/private/application.env
/var/tmp/aat-m2/cache/k3s kubectl --kubeconfig /var/tmp/aat-m2/secrets/kubeconfig \
  -n sistem-informasi-kebencanaan-bnpb create configmap aat-m2-storage-durability \
  --from-file=durability.json=evidence/storage-postgres/durability.json
/var/tmp/aat-m2/cache/k3s kubectl --kubeconfig /var/tmp/aat-m2/secrets/kubeconfig \
  apply -f evidence/aggregator-resources.json
```

These are explicit operator commands for later, not automatic actions by the
renderer. Secrets/config references and example endpoint names are deployment
inputs. The namespace must already exist. For the full formation, use the Citus
captured config/DSNs and set `storage_mode=citus`; this does not change the
existing separate multi-entity protocol gate. `--replicas 2` and `--replicas 5`
prepare the later load scenarios; no scaling command was executed.

The renderer explicitly enables source acquisition, canonical interfaces and
replicated durability. [Acquisition details](../../docs/Platform-Acquisition-Implementation.md)
explain election, cancellation and transactional stale-progress rejection.
Source leases are private to the process; canonical HTTP ownership routes cannot
issue acquisition tokens. Snapshot/processor authority, service isolation,
dependency deployments and full load/recovery evidence remain later work.

Deferred checks cover manifest resource/placement constraints, source
coordination, stale database effects and drain/readiness behavior. No runtime
acceptance status is inferred from a successful render or syntax check.

Scheduling and shutdown references: [Kubernetes topology spread](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/),
[pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination-flow).
